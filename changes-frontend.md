# Изменения frontend профориентационной системы

## Назначение документа

Этот файл — точка входа для разработчика, который впервые открывает frontend.
Он описывает актуальную структуру приложения, роли пользователей, основные
экраны, взаимодействие с backend и наиболее важные архитектурные решения.

Frontend отвечает только за интерфейс и вызовы Java backend. Он не обращается
напрямую к Python Prediction Service и не принимает решений о доступе к данным.

## Что изменилось в продукте

- Приложение сфокусировано на профориентации учеников.
- Удалены экраны HR, сотрудников компании и управления приглашениями.
- Компания оставлена как информационное место работы специалиста.
- Добавлены сущности `School` и `Curator`.
- Добавлено рабочее пространство куратора с учениками только его школы.
- Административные списки учеников и специалистов используют серверные
  фильтры и пагинацию.
- Добавлено управление активностью типов психологических и VR-тестов.
- Процесс расчёта профессии переведён на синхронную цепочку
  Frontend → Backend → Python → Backend.
- Унифицированы заголовки страниц, фильтры, диалоги подтверждения,
  состояния загрузки/пустого результата и отображение ошибок API.
- Роли `HR`, `EMPLOYEE`, `DIRECTOR`, `TEACHER`, `APPLICANT` больше не
  предоставляют пользовательские сценарии в этом frontend.

## Технологическая схема

```text
React + TypeScript + Vite
        |
        | Axios, JSON, Authorization: Bearer <JWT>
        v
Java backend /api/**
        |
        | только для расчёта профессии
        v
Python Prediction Service
```

Адрес backend задаётся переменной `VITE_API_URL`. Общий Axios-клиент находится
в `src/services/api/api.ts`.

## Роли и доступ

Активные роли описаны в `src/types/account/role.ts`, а повторно используемые
наборы доступа — в `src/routing/roleAccess.ts`.

| Роль | Основные возможности |
|---|---|
| `PUPIL` | Профиль, школа, предметы/оценки, тесты, результаты и Prediction |
| `SPECIALIST` | Профиль специалиста, психологические и VR-тесты, свои результаты |
| `CURATOR` | Ученики своей школы, фильтрация, сброс пароля, выгрузка результатов |
| `ADMIN` | Ученики, специалисты, школы, кураторы, тесты, справочники и симуляции |

`RolesProtectedRoute` запрашивает актуальные роли у backend. Cookie с ролями
может использоваться для построения меню, но не является источником
авторизации. Окончательное решение о доступе всегда принимает backend.

### Сценарий авторизации

```text
POST /api/auth/login
  -> backend возвращает строку Bearer <JWT>
  -> AuthContext сохраняет JWT без префикса Bearer в cookie token
  -> /api/auth/account-roles возвращает активные роли
  -> RolesProtectedRoute разрешает или отклоняет маршрут
```

При HTTP 401 или невалидном JWT пользователь должен быть выведен из сессии.

## Основные функциональные модули

### Ученики

`PupilsList` и `pupilApi` работают с серверной пагинацией. Поддерживаются
фильтры по ФИО, email, школе, классу и полу. Не следует повторно фильтровать
полный набор на клиенте: backend одновременно ограничивает выборку по роли и
школе куратора.

Администратор может назначить ученику структурированную школу. Старое
текстовое поле школы сохраняется backend для совместимости с мигрированными
данными.

### Школы и кураторы

`SchoolManagement` позволяет ADMIN:

- создавать и изменять школы;
- просматривать кураторов школы;
- создавать и редактировать кураторов.

`CuratorDashboard` позволяет CURATOR:

- видеть только учеников своей школы;
- использовать фильтры и пагинацию;
- сбрасывать пароль ученика после подтверждения;
- выгружать результаты своей школы за период в JSON или XLSX;
- переходить к собственному профилю.

Frontend не отправляет `schoolId` при запросе учеников или результатов
куратора. Школа определяется backend по JWT. Это важная граница безопасности.

### Специалисты и компании

Список специалистов использует серверные фильтры по имени, профессии и
компании. Компания — информационный справочник. Создание сотрудников,
HR-менеджеров и приглашений удалено из интерфейса.

### Типы тестов

Администратор может включать и выключать типы психологических и VR-тестов.
Обычному пользователю должны показываться только активные типы. Исторические
результаты выключенного теста не удаляются.

### Расчёт профессии

`predictionApi.ts` содержит два вызова:

- `POST /api/predictions/predict` — рассчитать и сохранить новый результат;
- `GET /api/predictions/latest` — получить последний сохранённый результат.

Frontend не передаёт `pupilId` и данные тестов. Backend получает ученика из JWT,
собирает его последние тесты и только затем вызывает Python.

```text
Predictions.tsx
  -> predictionAPI.predict(token)
  -> Java backend
  -> Python /predict
  -> Java сохраняет Prediction
  -> frontend отображает профессию, кластер, расстояние и категорию уверенности
```

## API-слой

Новый HTTP-вызов следует добавлять в тематический модуль `src/services/api`,
а его request/response — в `src/types`. Компонент не должен собирать URL или
разбирать внутреннюю структуру ошибки самостоятельно.

Основные модули:

| Файл | Назначение |
|---|---|
| `authApi.ts` | Login, роли и смена пароля |
| `pupilApi.ts` | Профиль и административный список учеников |
| `specialistApi.ts` | Специалисты и профессии |
| `educationApi.ts` | Школы, кураторы и их защищённые операции |
| `predictionApi.ts` | Запуск и чтение Prediction |
| `simulationApi.ts` | Симуляции и внешние данные |
| `vrTestsApi.ts` | VR-тесты и результаты |
| `error.ts` | Преобразование HTTP-ошибки в понятное сообщение |

Для отменяемых списочных запросов используется `AbortSignal`. Это защищает от
гонок при быстрой смене страницы или фильтров.

## Общие UI-правила

- Использовать `PageHeader`, `DataFilterBar`, `ConfirmDialog` и существующие
  состояния `NoResults` вместо локальных аналогов.
- Деструктивное или чувствительное действие требует явного подтверждения.
- Ошибки выводятся через `getApiErrorMessage` и toast.
- Кнопка отправки блокируется на время запроса.
- Пустой результат, загрузка и ошибка — разные состояния интерфейса.
- Экспорт строится из данных backend; клиент не расширяет область доступных
  пользователю записей.

## Удалённый legacy-контур

Удалены компоненты и типы, связанные с:

- HR-менеджерами;
- сотрудниками компаний;
- приглашениями;
- отдельным HR workspace;
- устаревшими дублирующими hooks тестового движка.

Не следует возвращать эти зависимости в новые компоненты. Если исторические
роли встречаются в JWT или базе, они не должны порождать маршруты или пункты
меню профориентационного продукта.

## Локальный запуск и проверка

```text
npm install
npm run dev
npm test -- --runInBand
npm run build
```

Минимальная конфигурация:

```text
VITE_API_URL=http://127.0.0.1:8082
```

На момент подготовки документа проходят 6 Jest-тестов и production build.
Vite предупреждает о крупном основном bundle; это не блокирует сборку, но при
дальнейшем росте приложения стоит добавить lazy routes и разделение чанков.

## Как безопасно расширять frontend

1. Сначала определить backend-контракт и роль пользователя.
2. Добавить типы в `src/types`.
3. Добавить вызов в `src/services/api`.
4. Использовать общий обработчик ошибок и состояния загрузки.
5. Добавить маршрут с правильным набором ролей.
6. Не передавать идентификатор владельца, ученика или школы, если backend может
   получить его из JWT.
7. Проверить desktop/mobile, пустые данные, 401/403/404 и повторную отправку.
8. Запустить Jest и production build.
